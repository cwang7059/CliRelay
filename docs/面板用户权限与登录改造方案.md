# CliRelay / Code Proxy 面板用户权限与登录改造方案

> 文档版本：v1.0  
> 更新日期：2026-06-22  
> 适用范围：CliRelay 后端（`CliRelay/`）+ 管理客户端（`codeProxy/`）

---

## 1. 背景与目标

### 1.1 现状

当前 CliRelay 管理端采用**单一共享密钥**认证，无用户表、角色或会话机制：

| 能力 | 当前机制 |
|------|---------|
| 管理后台 `/v0/management/*` | 一个 `remote-management.secret-key`（bcrypt）或 `MANAGEMENT_PASSWORD` 环境变量 |
| codeProxy 登录 | 用户手动填写**服务地址（IP:端口）+ 管理密钥** |
| 代理 API Key | 供 Codex/客户端调用模型，**不能**进入管理后台 |
| 角色权限 | 无。持有管理密钥 = 全部管理权限 |

### 1.2 改造目标

1. **用户名 + 密码登录**，替代向普通用户暴露管理密钥
2. **隐藏服务 IP/端口**：桌面安装包内置服务地址，用户无需手动填写
3. **权限分级**：`admin` 拥有全部权限；`user`（普通用户）仅能访问授权范围内的只读/自助功能
4. **可落地、可分期**：先上线可用版本，再迭代数据隔离与审计

### 1.3 不在本方案范围内

- 代理 API Key 的模型/渠道配额体系（已有，与面板用户体系独立）
- 企业 SSO / OAuth 外部身份源（可作为后续扩展）
- 多租户（一套服务多个完全隔离的组织）

## 2. 角色定义

第一版仅实现两个角色，满足绝大多数场景：

| 角色 | 标识 | 定位 | 典型使用者 |
|------|------|------|-----------|
| 超级管理员 | `admin` | 全部页面可见、全部 API 可操作 | 服务负责人、运维 |
| 普通用户 | `user` | 只读观察 + 个人 API Key 自助 | 开发同事、业务同学 |

> 后续如需可增加 `operator`（只读 + 代管 Key，不改配置），第一版不必实现。

### 2.1 与代理 API Key 的区别

| | 面板用户（本方案） | 代理 API Key（已有） |
|--|-------------------|---------------------|
| 用途 | 登录管理后台 | Codex/客户端调用模型 API |
| 认证方式 | 用户名 + 密码 → Session Token | `Authorization: Bearer sk-xxx` |
| 权限范围 | 管理面板功能（按角色） | 模型/渠道/配额限制 |
| 普通用户场景 | 看监控、查日志、管理自己的 Key | 实际发起推理请求 |

## 3. 普通用户可见内容（页面级）

对照 codeProxy 现有侧边栏四组导航。

### 3.1 观察组 — 全部开放（只读）

| 页面 | 路由 | 普通用户 | 说明 |
|------|------|---------|------|
| 仪表盘 | `/dashboard` | ✅ 可见 | KPI、吞吐趋势、系统监控卡片；**隐藏**初始化清单中创建 Key / Auth 文件的跳转 |
| 监控 | `/monitor` | ✅ 可见 | 概览 + 请求日志；API Key 列脱敏显示（如 `sk-abc***xyz`） |
| 日志 | `/logs` | ✅ 可见 | 应用/错误日志只读；**禁止**清空、删除 |

### 3.2 资源组 — 部分只读

| 页面 | 路由 | 普通用户 | 说明 |
|------|------|---------|------|
| 模型库 | `/models` | ✅ 只读 | 查看可用模型列表、同步状态；不可增删改 |
| AI 供应商 | `/ai-providers` | ❌ 不可见 | 含上游 Key，高度敏感 |
| 渠道路由 | `/channel-groups` | ❌ 不可见 | 路由策略，属运维配置 |
| 代理池 | `/proxies` | ❌ 不可见 | 出口代理配置 |
| 图像生成 | `/image-generation` | ❌ 不可见 | 含测试调用，易滥用资源 |

### 3.3 安全组 — 仅个人 Key

| 页面 | 路由 | 普通用户 | 说明 |
|------|------|---------|------|
| API Keys | `/api-keys` | ⚠️ 受限 | **仅看自己名下的 Key**；可复制、查看用量；不可创建/删除他人 Key |
| Auth 文件 | `/auth-files` | ❌ 不可见 | OAuth 上游凭证，最高敏感 |
| Key 权限模板 | `/api-key-permissions` | ❌ 不可见 | 全局策略模板 |
| 身份指纹 | `/identity-fingerprint` | ❌ 不可见 | 反检测配置 |

### 3.4 系统组 — 基本关闭

| 页面 | 路由 | 普通用户 | 说明 |
|------|------|---------|------|
| 配置 | `/config` | ❌ 不可见 | YAML / 可视化配置 |
| 系统 | `/system` | ⚠️ 极简子集 | 桌面端仅保留：**一键连接 Codex**（使用自己的 Key）、修改自己的密码；不显示服务地址、管理密钥、升级入口 |

### 3.5 其他入口

| 入口 | 路由 | 普通用户 | 说明 |
|------|------|---------|------|
| API Key 自查 | `/apikey-lookup` | ✅ 保持公开 | 现有逻辑：凭 API Key 查询个人用量，无需面板登录 |
| 侧边栏角色标签 | — | 动态显示 | 显示「管理员」或「普通用户」，不再写死 Super Admin |
| 登录页 | `/login` | 用户名 + 密码 | 桌面安装包**不显示**服务器地址字段 |

### 3.6 管理员可见范围

**admin = 现有全部页面 + 全部 API**，并新增：

- **用户管理**（新页面 `/users`）：创建/禁用用户、重置密码、分配角色、绑定 API Key
- 保留 `secret-key` 作为 **break-glass** 紧急管理员入口（可选，建议保留）

## 4. 后端 API 权限（路由级 RBAC）

前端隐藏菜单不足以保证安全，**后端必须拦截越权请求**。

### 4.1 设计原则

- **V1（第一版）**：路由级 RBAC — 按 HTTP 方法 + 路径白名单控制
- **V2（迭代）**：数据级隔离 — 按 `user_id` 过滤 API Key、用量、日志

### 4.2 普通用户 API 白名单（V1）

**允许的 GET 请求：**

```
/dashboard-summary
/system-stats
/system-stats/ws
/usage
/usage/export
/usage/logs
/usage/logs/:id/content
/usage/auth-file-group-trend
/usage/auth-file-trend
/usage/chart-data
/usage/entity-stats
/logs
/request-error-logs
/request-error-logs/:name
/request-log-by-id/:id
/request-log
/models
/model-configs
/channel-groups
/api-key-entries          # 返回时按 user_id 过滤
/api-keys                 # 返回时按 user_id 过滤
/latest-version
/auth/me
```

**允许的写操作：**

```
POST /auth/logout
PUT  /auth/password       # 仅修改自己的密码
```

**一律返回 403 的请求（普通用户）：**

- 所有其他 `PUT` / `PATCH` / `DELETE` / `POST`
- `/config*`、`/config.yaml`
- `/management-key`
- `/update/*`
- `/auth-files*`、各 `*-api-key`（供应商 Key）
- `/oauth-*`、`/vertex/import`
- `/proxy-pool`、`/routing-config`、`/identity-fingerprint`
- `/api-key-permission-profiles`
- `/users/*`（用户管理，仅 admin）

### 4.3 管理员 API 权限

`admin` 角色可访问现有全部 `/v0/management/*` 端点，行为与当前 management key 一致。

## 5. 认证架构

### 5.1 登录流程

```
┌─────────────┐     HTTPS      ┌──────────────┐     内网      ┌───────────┐
│ codeProxy   │ ──────────────►│ Nginx/Caddy  │ ────────────► │ CliRelay  │
│ 桌面/浏览器  │                │ admin.xxx.com│               │  :8317    │
└─────────────┘                └──────────────┘               └───────────┘

1. POST /v0/management/auth/login  { username, password }
2. 服务端校验 bcrypt 密码，创建 session，返回 { token, role, username, expires_at }
3. 后续请求：Authorization: Bearer <session-token>
4. Middleware 校验 token → 注入 user_id + role → RBAC 检查 → 业务处理
```

### 5.2 Middleware 认证优先级

1. `Authorization: Bearer <session-token>` → 查 `panel_sessions` 表 → 注入 `user_id`、`role`
2. 否则匹配现有 `secret-key` / `MANAGEMENT_PASSWORD` → 视为 **admin**（兼容旧客户端与紧急入口）
3. 认证失败 → `401`；角色不足 → `403`

### 5.3 新增数据表（SQLite，与现有 usage DB 同库）

```sql
-- 面板用户
CREATE TABLE panel_users (
  id            TEXT PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,          -- bcrypt
  role          TEXT NOT NULL CHECK(role IN ('admin', 'user')),
  disabled      INTEGER NOT NULL DEFAULT 0,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  last_login_at TEXT
);

-- 会话（推荐不透明 token，便于吊销）
CREATE TABLE panel_sessions (
  token       TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES panel_users(id),
  expires_at  TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  ip          TEXT,
  user_agent  TEXT
);

-- V2：用户与 API Key 绑定
CREATE TABLE panel_user_api_keys (
  user_id     TEXT NOT NULL REFERENCES panel_users(id),
  api_key_id  TEXT NOT NULL,
  PRIMARY KEY (user_id, api_key_id)
);
```

### 5.4 新增 API 端点

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| `POST` | `/v0/management/auth/login` | 公开（限流） | 用户名密码登录 |
| `POST` | `/v0/management/auth/logout` | 已登录 | 吊销当前 token |
| `GET` | `/v0/management/auth/me` | 已登录 | 返回 `{ username, role, permissions[] }` |
| `PUT` | `/v0/management/auth/password` | 已登录 | 修改自己的密码 |
| `GET` | `/v0/management/users` | admin | 用户列表 |
| `POST` | `/v0/management/users` | admin | 创建用户 |
| `PUT` | `/v0/management/users/:id` | admin | 更新用户（角色、禁用状态） |
| `DELETE` | `/v0/management/users/:id` | admin | 删除/禁用用户 |
| `POST` | `/v0/management/users/:id/reset-password` | admin | 重置用户密码 |
| `PUT` | `/v0/management/users/:id/api-keys` | admin | 为用户绑定 API Key |

### 5.5 Session 策略

| 参数 | 建议值 |
|------|--------|
| Token 类型 | 不透明随机字符串（非 JWT，便于服务端吊销） |
| 有效期 | 24 小时（可配置） |
| 存储 | `panel_sessions` 表 |
| 限流 | 登录接口：同 IP 5 次失败 → 30 分钟封禁（复用现有 management 限流逻辑） |

## 6. 隐藏服务地址

### 6.1 部署层

```
公网只暴露：https://admin.yourdomain.com
内网反代到：  http://127.0.0.1:8317
8317 端口不对公网开放
```

配置要求：

- `remote-management.allow-remote: true`（仅反代可达）
- Nginx/Caddy 配置 HTTPS 证书
- 可选：限制来源 IP 或加 WAF

### 6.2 客户端构建层

安装包构建时注入环境变量：

```
VITE_DEFAULT_API_BASE=https://admin.yourdomain.com
VITE_HIDE_API_BASE=true
```

Electron `main.cjs` 默认使用上述地址，登录页不显示「服务器地址」输入框（高级模式可选开启）。

### 8.2 RBAC 中间件伪代码

```go
func (h *Handler) RBACMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        role := c.GetString("panel_role") // "admin" | "user"
        if role == "admin" {
            c.Next()
            return
        }
        method := c.Request.Method
        path := c.FullPath()
        if isUserAllowed(method, path) {
            c.Next()
            return
        }
        c.AbortWithStatusJSON(403, gin.H{"error": "permission denied"})
    }
}
```

## 10. 初始化与日常运维

### 10.1 首次部署流程

1. 部署 CliRelay，配置 `secret-key`（仅保存在服务器，不告知普通用户）
2. 首次访问管理端 → 系统引导创建 `admin` 账号（或自动从 secret-key 初始化）
3. admin 登录 → 进入「用户管理」创建普通用户（如 `alice`）
4. admin 为 `alice` 创建并绑定 API Key（如 `sk-alice-xxx`）
5. 分发桌面安装包给 `alice`，她使用用户名 + 密码登录即可

### 10.2 日常运维

| 场景 | 处理方式 |
|------|---------|
| 普通用户忘记密码 | admin 在「用户管理」重置密码 |
| 普通用户需要 API Key | admin 创建 Key 并绑定到该用户 |
| 紧急恢复（面板不可用） | 使用服务器上的 `secret-key` 直接调 API（break-glass） |
| 员工离职 | admin 禁用账号 + 吊销其 API Key |

## 13. 风险与注意事项

| 风险 | 缓解措施 |
|------|---------|
| 仅前端藏菜单，后端未拦截 | 阶段 1 必须同步实现 RBAC 中间件 |
| Session token 泄露 | HTTPS 强制、合理过期时间、支持吊销 |
| 旧客户端仍用 management key | 保留 secret-key 兼容，逐步迁移 |
| 普通用户通过 API 直接调敏感端点 | 白名单 + 集成测试覆盖 403 |
| Windows SmartScreen 拦截未签名安装包 | 后续考虑代码签名证书 |
| `nsis` 与 `portable` 产物文件名冲突 | 打包时分开构建或配置不同 `artifactName` |
